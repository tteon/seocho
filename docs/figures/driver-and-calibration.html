Does a native driver matter, and does the offline cost model hold?

Two questions that were open, now measured. Both were asked because an earlier statement of mine was too loose: I said driver overhead was negligible, and I said the cost model held “across five orders of magnitude”. Neither survived contact with the numbers unchanged.

chart 1 — per-row cost

Where the client time goes, normalised per row

Absolute totals differ 50× between the two row counts, so plotting them together would hide the small bars. Per-row cost puts both drivers on one axis — and the fact that each driver’s per-row cost is flat across row counts is itself the finding: this is a fixed charge per row, not a warm-up effect.

What this does not license. The agent query path caps results at 50 rows, where the 5.1× is worth about 0.6 ms against 37 seconds of model time. A native driver is justified here by what it can enforce, not by speed — see the early-abort row above, which applies a bound to a query whose text has no LIMIT for any query-level guardrail to inspect.

table — locating the cost

The charge is per row, not per value

Holding rows fixed at 50,000 and going from one returned column to five multiplies the values by five. If cost scaled with values, the total would roughly quintuple.

1 column12.2 ms694.2 ms13.88 µs13.88 µs
5 columns14.8 ms760.9 ms15.22 µs3.04 µs

Five times the values added 66.7 ms, not 2,800 ms. Working it through: roughly 13.6 µs fixed per row and 0.33 µs per additional field. The cost is constructing one Python Record object per row; filling it is nearly free.

Correction. I earlier described this as “decoding is free, the cost is transport”, comparing Python’s 11 ms to neo4rs’ 129 ms. Those are not the same operation: Python’s 11 ms sends DISCARD, so the server never transmits the rows at all, while the neo4rs figure pulls and parses all 50,000. The comparable pair is full decode — 694 ms against 140 ms. Within neo4rs, typed field extraction adds only 2% (129 → 132 ms), and that narrow step is the only thing “free” describes.

chart 2 — cost model calibration

Where the offline estimate stops predicting engine work

Each point is one anchor: its measured database hits divided by L2, the neighbourhood size computed offline from Parquet before any query runs. A flat line at 2.0 means the estimate converts to engine work by a constant.

Correction. The claim was “≈2× across five orders of magnitude”. The plateau is real from L2 3,773 to 15,973,145 — four orders — and the estimate under-predicts below roughly 3,800, reaching 14.6× at the floor where fixed per-query cost dominates. That direction is harmless for a cost gate: it over-states the cost of queries that are cheap anyway. I also briefly reported the constant as breaking at the top end, reading a band mean of 1.02; that was an artefact of a timed-out anchor contributing its L2 to the estimate while contributing no measurement.

The decisive pair is a single anchor — account 0, L2 51,447,907 — separated by hop count alone: one hop cleared and returned 154,077 hits; two hops was flagged and timed out. Same node, same data, same code.

  • A false clear is the failure the gate exists to prevent.
  • A false flag trades answer quality for safety — a tuning question, not a broken premise.
  • The one false flag in the first run was a bug of mine: anchor extraction required four or more digits, so account number 0 — the most expensive anchor in the dataset — parsed as unanchored.

for your check

Three judgement calls I would like confirmed

  • Chart 1 is normalised per row rather than showing totals. Totals span 3.3 ms to 648 ms, so a shared linear axis would flatten the 1,000-row bars to nothing. Per-row also makes the flatness visible. Totals are in the tooltips and the table.
  • Chart 2 plots a ratio, not two cost lines. A ratio shows the constant directly; plotting estimate and measurement as two series on a log axis would look like agreement everywhere and hide the divergence at the floor.
  • Run-to-run variance is not shown. Two neo4rs runs gave 131.7 ms and 140.4 ms for the same query (6.6% apart), and early-abort saving of 170× and 194×. Figures here are the saved run. If these go in a deck I would rather report a range.
