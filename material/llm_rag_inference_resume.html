API-Based Graph-RAG / Product Runtime

  • Problem: graph retrieval was assumed to help financial QA. Built a FinDER-style study on 910 financial QA rows across six slices to compare vector, graph, and vector+graph modes with ontology size as a controlled variable.
  • Problem: decision-thread QA looked graph-friendly. Ran 135 cases x 5 lanes = 675 comparison runs on BC3 and found vector/hybrid remained stronger than graph-only, changing the product direction from "graph always wins" to route-by-query and evidence-first answering.
  • Problem: graph context can be larger and expensive. Measured KV-cache cost behavior on BC3: graph context reached a 59% cached-token hit ratio vs vector 0%, with lower amortized billable prompt tokens despite 2.2x larger raw context.
  • Problem: final answers could hide missing graph evidence. Added route and evidence contracts so required slots, missing slots, provenance, route profile, and answer shape remain visible before answer synthesis.
  • Converted API-model limitations into product design: ontology guardrails, context graph, route profiles, and evidence bundles compensate for not owning the foundation model while keeping outputs auditable.
  • Profiled DozerDB/Neo4j graph hydration and adopted a Rust PackStream codec: 1.62x faster real 3-shard federation read and 3.57x faster 130k-row bulk hydration with hash-parity checks.
